## กติกาของเกม

- **บอส** คือ milestone หนึ่งขั้น win conditions ต้องตรวจได้จริง เช่น ตัวเลข รันซ้ำได้ผลเดิม หรือตอบคำถามได้ ไม่ใช่แค่ "รู้สึกว่าเข้าใจแล้ว"
- **ตาย:** พอคุณส่งงาน ผมจะรันโค้ดจริงแล้วเช็กทีละข้อ ข้อที่ไม่ผ่าน ผมจะบอกว่าข้อไหนตกและเห็นอาการอะไร แต่จะไม่บอกวิธีแก้ ตายได้ไม่จำกัดครั้ง
- **Summon (ขอ hint)** เรียกได้ทุกเมื่อ ไม่ถือว่าผิด แต่ผมจะจดลง Progress log ท้ายไฟล์นี้ตามจริง มี 4 ระดับ:
  - **S1 ทิศทาง:** ควรมองตรงไหน
  - **S2 ชื่อ concept หรือเทคนิค**
  - **S3 pseudo-code**
  - **S4 โค้ดเต็ม:** ให้เฉพาะเมื่อคุณขอชัด ๆ
- **Solo clear:** ผ่านบอสโดยใช้ hint ไม่เกิน S2 นับเป็นหลักฐานว่า "ทำได้เอง" (สถานะ `solid` ใน skill map ของ `../LEARNING_LOG.md`)
  ถ้าใช้ S3 หรือ S4 ถือว่าผ่านแบบ guided (สถานะยังเป็น `learning`) และบอสนั้นจะมี rematch สั้น ๆ ในภายหลัง
- **ซักถามหลังชนะ:** 3 คำถามแบบปิดโน้ต และโจทย์ดัดแปลง 1 ข้อ (transfer) ถ้าไม่ผ่าน บอสยังไม่ตาย
- **Checkpoint:** หลังชนะบอส ให้ commit และเขียน `../LEARNING_LOG.md` ด้วยตัวเอง
- **หมอกบัง:** บอสถัดไปบอกแค่เป้าหมายคร่าว ๆ รายละเอียดและ win conditions เต็มจะเปิดเมื่อไปถึง เพราะต้องปรับตาม metric และสิ่งที่เจอในข้อมูลจริง
- **ผมไม่เขียนโค้ดที่เป็นคำตอบ** ที่ผมเขียนได้คือ "สนามประลอง" เช่น trap dataset หรือ script ตรวจผลที่ไม่เฉลย

## มาตรฐานการตัดสิน: ระดับ engineer แนวหน้า

ผมจะตรวจงานแบบ senior reviewer ในทีมระดับแนวหน้า ไม่ใช่แบบแบบฝึกหัดในคอร์ส:
- **ทุก claim ต้องมีหลักฐาน:** ที่ตอบว่า "น่าจะ" หรือ "รู้สึกว่า" โดยไม่มีตัวเลขหรือผลทดลองรองรับ ไม่นับ
- **ตัวเลขต้องมาพร้อม uncertainty:** คะแนนตัวเดียวโดด ๆ ไม่มีความหมาย ต้องบอกได้ว่าแกว่งได้แค่ไหน
- **อธิบายกลไกได้ถึงระดับคณิตศาสตร์หรือ implementation:** แค่รู้ว่าใช้ function ไหนไม่พอ
- **โค้ดต้องมีคุณภาพระดับ PR:** รันซ้ำได้ อ่านรู้เรื่อง ส่งให้ทีมอื่น review ได้ทันที
- **การตัดสินใจต้องเขียนไว้:** มีทางเลือกอะไรบ้าง เลือกทางไหน เพราะอะไร และยอมเสียอะไรไป
- **ถูกแบบบังเอิญไม่นับ:** ถ้าคำตอบถูกแต่เหตุผลผิด ถือว่าตาย

ค่าประมาณ: บอสละ 1–2 sessions (session ละ 2–3 ชั่วโมง)

## ⚔️ Boss 1: The Hollow Label

**ทักษะ:** problem framing, metric, target ที่หาย, baseline

**ทำไมบอสนี้สำคัญ:** โมเดลที่ดีที่สุดก็ไร้ค่าถ้าตอบผิดคำถาม หรือวัดด้วยไม้บรรทัดผิดอัน
และถ้าไม่รู้ว่าการ "ไม่ทำอะไรเลย" ได้คะแนนเท่าไหร่ คุณจะไม่มีทางรู้ว่าโมเดลเก่งจริงหรือไม่

**ส่งงาน:**
- `NOTES.md` หัวข้อ `Framing`
- `baseline.py` หรือใช้ cell ใน `eda.py` ก็ได้ แต่ต้องรันจากบนลงล่างจบได้ในครั้งเดียว

### Win conditions

1. **Framing:** หนึ่งแถวแทนอะไร target คืออะไร positive class คืออะไร submission ต้องส่ง label หรือ probability และ metric ทางการคืออะไร ทั้งหมดนี้ต้องอ้างอิงหน้า Evaluation ของ competition
2. **ตัวเลขตั้งต้น:** จำนวนแถวของ train และ test, positive rate (คิดเฉพาะแถวที่มี label), จำนวนและ % ของแถวที่ target หาย
3. **แถวที่ target หาย:** เลือกทางจัดการมาทางเดียว พร้อมหลักฐานอย่างน้อย 2 ชิ้น
   เขียนด้วยว่าการตัดสินใจนี้ตั้งอยู่บน assumption อะไร และถ้า assumption ผิดจะเกิดอะไรขึ้น
4. **Baseline ladder** บน hold-out ที่คุณแบ่งเอง โดยกำหนด seed คงที่:
   - (ก) ทำนายเป็นค่าคงที่ อย่างน้อย 2 แบบที่ต่างกัน
   - (ข) โมเดลที่ใช้ feature เดียวที่ดีที่สุด

   **กฎพิเศษ:** ก่อนรัน (ก) ต้องเขียนคำทำนายคะแนน พร้อมเหตุผลทางคณิตศาสตร์ ลง `NOTES.md` ก่อน แล้วค่อยเทียบกับผลจริง
   ทายผิดไม่นับว่าตาย แต่ต้องอธิบายให้ได้ว่าทำไมผิด

   **กฎระดับแนวหน้า:** คะแนนของ (ข) ต้องรายงานพร้อมช่วงความไม่แน่นอน และต้องบอกได้ว่าวิธีที่ใช้คำนวณช่วงนั้นตั้งอยู่บน assumption อะไร
   แล้วตอบให้ได้ว่า hold-out ขนาดนี้แยก "โมเดลที่ดีกว่าจริง" ออกจาก "โชค" ได้ละเอียดแค่ไหน
5. **Reproducible:** รัน `uv run python baseline.py` จาก `heart_disease/` กี่ครั้งก็ต้องได้ตัวเลขเดิม
6. **ซักถาม:** ผ่าน 3 คำถามและโจทย์ transfer 1 ข้อ

### เส้นทางแนะนำ (บอกทาง ไม่บอกคำตอบ)

1. อ่านหน้า Overview, Evaluation และ Data ของ competition ให้จบก่อนแตะโค้ด
2. ตอบตัวเองให้ได้ว่า metric นี้ "ให้รางวัล" กับอะไร มันสนใจ ranking, ความถูกของ probability หรือการตัดสินใจ yes/no
3. แถวที่ target หาย: เทียบไม่ใช่แค่ระหว่างกลุ่มที่หายกับไม่หาย แต่เทียบกับข้อมูลชุดอื่นที่มีด้วย
4. ก่อนเขียนโค้ด baseline ให้ถามตัวเองว่า metric นี้ทำอะไรกับการทำนายที่ "เท่ากันทุกแถว"

## 🌫️ บอสถัดไป (หมอกบัง)

**Boss 2: The Mirror of Folds:** สร้าง CV harness ที่เชื่อถือได้ แล้วพิสูจน์ด้วย submission จริงว่า CV ทำนาย public LB ได้
บอสนี้จะให้ "noise floor" ที่บอส 4–5 ต้องใช้ตัดสินว่าอะไรคือการปรับปรุงจริง

**Boss 3: The Leak:** สร้าง leak ด้วยมือตัวเองให้คะแนนพองจนเห็นชัด แล้วซ่อมให้ได้
จากนั้นล่า leak ที่ผมซ่อนไว้ใน trap dataset ต้องพิสูจน์ด้วยหลักฐาน ห้ามเดา

**Boss 4: The Linear Knight:** linear baseline ที่แข็งแรง ทุก feature ที่เก็บไว้ต้องผ่านเกณฑ์การยอมรับ และต้องมี experiment log

**Boss 5: The Hydra:** gradient boosting ที่ early stopping ไม่ leak และ tuning ภายใต้ budget จำกัด
ต้องชนะบอส 4 เกิน noise floor หรือไม่ก็พิสูจน์ได้ว่าทำไม linear ชนะ

**Boss 6: The Threshold Oracle:** calibration, เลือก threshold จาก cost ของการตัดสินใจทางคลินิก และหาว่าโมเดลพังในกลุ่มย่อยไหน
